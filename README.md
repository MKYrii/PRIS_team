## 1. Цели и предпосылки

### 1.1 Зачем идём в разработку продукта?

Платформа ежедневно получает **до 500 000 комментариев**. Ручная модерация не справляется с таким объёмом: модераторы просматривают лишь выборку, что создаёт риски:

- **Регуляторные**: РКН ведёт мониторинг качества модерации; пропущенный запрещённый контент — штрафы и блокировки.
- **Репутационные**: негативные или токсичные комментарии снижают вовлечённость аудитории и отпугивают рекламодателей.
- **Операционные**: содержание команды ручных модераторов при 500K комментариев/день требует значительных затрат.

### 1.2 Почему ML улучшит ситуацию?

| Сейчас (as-is) | После внедрения (to-be) |
|---|---|
| Просмотр ~5–10% комментариев вручную | Автоматическая классификация 100% за < 300 мс |
| Субъективность оценки | Единый воспроизводимый критерий |
| Реакция через часы | Флаг + автоскрытие за секунды |
| Нет аналитики трендов | Дашборд тональности в реальном времени |
| Высокая стоимость модерации | Снижение затрат на 60–70% |

### 1.3 Бизнес-требования и ограничения

**Требования:**
- Обрабатывать пиковую нагрузку ≥ 500K комментариев/сутки (≈ 6 RPS средних, пики до 50 RPS).
- Precision по классу "нарушение" ≥ 0.90 (ложные блокировки раздражают пользователей).
- Recall по классу "нарушение" ≥ 0.85 (пропущенный запрещённый контент — регуляторный риск).
- Latency инференса ≤ 300 мс на комментарий (p95).
- Полный аудит решений для ответа на жалобы пользователей и РКН.

**Ограничения:**
- Контент на русском языке (основной), частично другие языки СНГ.
- Нельзя хранить персональные данные без согласия (ФЗ-152).
- Модель должна быть объяснимой для ответов регулятору.

### 1.4 Функциональные и нефункциональные требования

**Функциональные:**
- Классификация тональности: позитивная / нейтральная / негативная.
- Детекция нарушений: токсичность, hate speech, призывы к насилию, спам, NSFW-текст.
- Скоринг: вероятность нарушения [0, 1] для приоритизации ручной проверки.
- API для интеграции с существующей платформой.
- Дашборд: тренды тональности, топ-контент по реакциям, очередь модераторов.
- Feedback-петля: модераторы помечают ошибки → переобучение.

**Нефункциональные:**
- Доступность: SLA 99.9% (≤ 8.7 ч даунтайма/год).
- Масштабируемость: горизонтальное масштабирование воркеров инференса.
- Наблюдаемость: метрики, логи, трейсы (OpenTelemetry).
- Безопасность: авторизация по API-key, шифрование данных at-rest и in-transit.

### 1.5 Процесс пилота и критерии успеха

**Длительность пилота:** 4 недели.

**Схема:**
1. Недели 1–2: shadow mode — система работает параллельно с модераторами, решения не применяются. Сбор разметки.
2. Недели 3–4: A/B — 50% трафика проходит через автомодерацию (низкоуверенные кейсы идут к модераторам).

**Критерии успеха пилота:**

| Метрика | Порог успеха |
|---|---|
| Precision (нарушение) | ≥ 0.88 |
| Recall (нарушение) | ≥ 0.82 |
| Доля комментариев, уходящих на ручную проверку | ≤ 15% |
| Среднее время реакции на нарушение | ≤ 60 сек |
| Жалобы пользователей на ошибочную блокировку | не растут относительно baseline |

### 1.6 MVP vs технический долг

**MVP (итерация 1, ~8 недель):**
- Бинарный классификатор "нарушение / норма" на базе дообученной модели (ruBERT / multilingual BERT).
- REST API для интеграции с платформой.
- Очередь для асинхронной обработки (Kafka).
- Базовый дашборд для команды модерации.
- Пайплайн дообучения по фидбэку модераторов (раз в неделю).

**Технический долг (итерации 2+):**
- Мультиклассовая классификация типов нарушений.
- Анализ тональности (позитив/негатив/нейтрал) для маркетинговой аналитики.
- Детекция emerging-угроз (новый тип контента) через anomaly detection.
- Мультимодальный анализ (текст + изображения в комментариях).
- Персонализация (паттерны конкретного пользователя).
- Explainability-слой (highlight токенов, вызвавших флаг).

## 2. Методология

### 2.1 Техническая постановка задачи

**Основная задача:** Многоклассовая классификация текстов.

**Архитектура модели:**
- Backbone: `cointegrated/rubert-tiny2` (быстрый, < 30 мс) или `DeepPavlov/rubert-base-cased` (точнее, ~80 мс). Выбор по результатам бенчмарка на пилоте.
- Fine-tuning: на размеченном корпусе комментариев платформы.
- Inference: ONNX Runtime или TorchServe для ускорения.

**Классы (MVP):**
```
0 — норма
1 — нарушение (токсичность, hate speech, угрозы, спам, запрещённый контент)
```

**Расширение (v2):**
```
0 — норма
1 — токсичность / оскорбления
2 — hate speech
3 — угрозы насилия
4 — спам / реклама
5 — NSFW-текст
6 — дезинформация
```

### 2.2 Данные

**Обязательные источники:**

| Источник | Объём | Назначение |
|---|---|---|
| Исторические решения модераторов (последние 2 года) | ~5M записей | Обучение |
| Публичные датасеты (RuToxic, RuHateSpeech) | ~300K записей | Обучение (дополнение) |
| Фидбэк модераторов в реальном времени | Ongoing | Дообучение |
| Комментарии с context (пост + комментарий) | Все комментарии | Инференс |

**Без чего нельзя решить задачу:**
- Размеченный корпус ≥ 100K примеров, сбалансированный по классам (нарушения — редкий класс, нужен oversampling/focal loss).
- Разметка должна учитывать контекст: один и тот же текст может быть нормой или нарушением в зависимости от поста.

**Предобработка:**
- Нормализация: удаление лишних пробелов, приведение к нижнему регистру.
- Обработка эмодзи и специальных символов.
- Дедупликация (ботовые кампании дают идентичные комментарии).
- Обфускация (1337-speak, разбавление пробелами) — необходим аугментация датасета.

### 2.3 Метрики качества

**ML-метрики:**

| Метрика | Целевое значение | Связь с бизнесом |
|---|---|---|
| Precision (нарушение) | ≥ 0.90 | Число ложных блокировок нормальных комментариев |
| Recall (нарушение) | ≥ 0.85 | Доля реальных нарушений, пойманных системой |
| F1-score (macro) | ≥ 0.87 | Баланс |
| AUC-ROC | ≥ 0.95 | Качество ранжирования для приоритизации очереди |
| Latency p95 | ≤ 300 мс | SLA платформы |

**Бизнес-метрики (после внедрения):**
- Снижение затрат на модерацию ($/месяц).
- Время реакции на нарушение (секунды vs часы).
- Количество предписаний от РКН.
- Индекс токсичности дискуссий (вовлечённость аудитории).

### 2.4 Риски на этапе моделирования

| Риск | Вероятность | Митигация |
|---|---|---|
| Дисбаланс классов (нарушения — < 5% трафика) | Высокая | Oversampling (SMOTE для текстов), focal loss, threshold tuning |
| Adversarial inputs (обфускация) | Высокая | Аугментация датасета с намеренными ошибками |
| Дрейф данных (новый сленг, события) | Высокая | Мониторинг distribution shift, плановый retrain |
| Недостаточно размеченных данных | Средняя | Активное обучение (active learning), краудсорсинг разметки |
| Предвзятость (bias) по группам пользователей | Средняя | Fairness-аудит по срезам, bias-mitigation техники |
| Ложные блокировки контента журналистов/НКО | Средняя | Whitelist авторов, second-pass review для верифицированных аккаунтов |

## 3. Подготовка пилота

### 3.1 Схема оценки

```
Неделя 1–2: Shadow Mode
  ┌──────────────────────────────────────┐
  │  Входящие комментарии (100% трафика) │
  └──────────────┬───────────────────────┘
                 │
         ┌───────┴────────┐
         ▼                ▼
   Ручная модерация    ML-система
   (продакшн)          (тень, без применения)
         │                │
         └───────┬─────────┘
                 ▼
           Сравнение решений
           → разметка ошибок
```

```
Неделя 3–4: A/B (50/50)
  ┌──────────────────────────────────────────────────┐
  │  Входящие комментарии                            │
  └──────────────┬───────────────────────────────────┘
                 │
       ┌─────────┴──────────┐
       │                    │
  Группа A (50%)       Группа B (50%)
  Ручная модерация     ML-автоматизация
                       + ручная для score 0.4–0.7
```

### 3.2 Что считаем успешным пилотом

Пилот считается успешным, если **все** условия выполнены:
1. Precision ≥ 0.88 на тестовой выборке (offline) и ≥ 0.85 online.
2. Recall ≥ 0.82 на тестовой выборке.
3. ≤ 15% комментариев группы B требуют ручного review (доля неуверенных).
4. Нет роста жалоб пользователей в группе B (χ²-тест, p > 0.05).
5. Latency p95 ≤ 300 мс под нагрузкой пилота.
6. Нет регуляторных инцидентов, напрямую связанных с пропуском ML-системы.

### 3.3 Подготовка пилота

**Технические работы:**
- Развернуть ML-сервис в staging, нагрузочное тестирование.
- Интегрировать с платформой в shadow-режиме (без применения).
- Настроить A/B-роутинг на уровне API Gateway.
- Настроить сбор метрик: Prometheus + Grafana.
- Создать интерфейс разметки ошибок для модераторов.

**Организационные работы:**
- Обучить модераторов работе с новым дашбордом и очередью.
- Согласовать с юридическим отделом документацию для РКН.
- Определить on-call для инцидентов во время пилота.
- Установить процесс ежедневного review метрик.

## 4. Архитектура production-системы

### 4.1 Общая архитектура

Система построена на **event-driven** принципе с разделением на три плоскости:
- **Realtime-плоскость**: мгновенная классификация новых комментариев.
- **Аналитическая плоскость**: агрегация и дашборды.
- **ML-плоскость**: обучение, версионирование, A/B моделей.

Подробная диаграмма: [`diagrams/architecture.md`](diagrams/architecture.md)

### 4.2 Компоненты системы

| Компонент | Технология | Назначение |
|---|---|---|
| API Gateway | Kong / Nginx | Роутинг, rate limiting, auth |
| Comment Ingest Service | Python FastAPI | Приём событий от платформы |
| Message Broker | Apache Kafka | Буферизация, гарантия доставки |
| ML Inference Service | Python + TorchServe / Triton | Классификация комментариев |
| Moderation Action Service | Go | Применение решений: скрытие, эскалация |
| Human Review Queue | PostgreSQL + UI | Очередь неуверенных кейсов для модераторов |
| Analytics Store | ClickHouse | OLAP по тональности, трендам |
| Model Registry | MLflow | Версионирование моделей |
| Feature Store | Redis | Кэш фич пользователя |
| Dashboard | Grafana + Superset | Мониторинг и аналитика |
| Cold Storage | S3-compatible | Сырые комментарии, аудит-лог |

### 4.3 Инфраструктура и масштабируемость

**Выбранная инфраструктура:** Kubernetes (managed, например Yandex Cloud Managed K8s или on-premise).

**Обоснование распределённого хранилища:**

Данные хранятся в нескольких местах по функциональному принципу:
- **Kafka**: временное хранение потока (retention 7 дней) — высокая пропускная способность.
- **PostgreSQL**: оперативные данные (очередь модераторов, решения последних 90 дней) — ACID-транзакции.
- **ClickHouse**: аналитические данные (агрегаты, тренды) — OLAP-запросы за миллисекунды.
- **S3**: холодное хранение (весь исторический архив, > 90 дней) — дешёвое, неограниченное.
- **Redis**: кэш (фичи пользователей, результаты недавних запросов) — latency < 1 мс.
- **MLflow**: артефакты моделей — версионирование, воспроизводимость.

**Масштабирование:**

```
Нагрузка пика: 50 RPS × 1 комментарий × ~100 мс инференс ≈ 5 параллельных воркеров
Плановый запас: ×3 → 15 воркеров ML Inference
HPA: 2–20 pod'ов по CPU/очереди Kafka
```

**Плюсы архитектуры:**
- Kafka изолирует пики нагрузки от ML-воркеров.
- Независимое масштабирование каждого компонента.
- Отказ Analytics Store не влияет на модерацию.
- Canary-деплой новых моделей без даунтайма.

**Минусы:**
- Высокая операционная сложность (много компонентов).
- Eventual consistency между слоями (комментарий скрыт, но в дашборде ещё «нормальный» ~2 сек).
- Kafka требует тщательной настройки retention и replication.

### 4.4 SLA и нефункциональные требования

| Параметр | Требование |
|---|---|
| Доступность | 99.9% (≤ 8.7 ч/год) |
| RPS (средний) | 6 RPS |
| RPS (пиковый) | 50 RPS |
| Latency инференса (p50) | ≤ 100 мс |
| Latency инференса (p95) | ≤ 300 мс |
| Latency инференса (p99) | ≤ 500 мс |
| E2E latency (от поступления до решения) | ≤ 5 сек |
| Throughput | 500K комментариев/сутки |
| RPO (потеря данных) | ≤ 1 час |
| RTO (восстановление) | ≤ 30 мин |

### 4.5 Риски и неопределённости

| Риск | Влияние | Вероятность | Митигация |
|---|---|---|---|
| Падение ML-сервиса | Высокое | Средняя | Fallback: все комментарии → ручная очередь |
| Изменения требований РКН | Критическое | Средняя | Гибкая архитектура классификатора, быстрый retrain |
| Атака ботов (flood 10x нагрузки) | Высокое | Средняя | Rate limiting на Gateway, Kafka как буфер |
| Drift модели (новый сленг) | Высокое | Высокая | Мониторинг метрик + автоматические алерты |
| Утечка персональных данных | Критическое | Низкая | Анонимизация перед сохранением, RBAC, аудит-лог |
| Ложные блокировки → публичный скандал | Высокое | Средняя | Порог уверенности, instant appeal-процесс |
